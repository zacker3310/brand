# Data-integrity audit deep-2: Spectrum, Ant Design, MUI and NHS families

Audit date: 2026-11-05. Auditor: deep-2 (adversarial). Database: dev catalog `atlas`. Scope: adobe-spectrum, react-spectrum, react-aria, ant-design, ant-design-mobile, mui, joy-ui, base-ui, nhs-design-system (adapters `spectrum`, `antd`, `mui`, `govuk` NHS profile).

The goal was to refute what ATLAS publishes. Every check below compares a stored claim with the live official source it cites, not with ATLAS's own evidence rows.

## Method

1. **Sample.** For each system, 6 published components ordered by `md5(id::text || 'deep-2')`. The order is reproducible, and component ids survive re-ingestion because publish upserts on natural keys. Each component also contributes 3 variants or sizes or states and 3 properties in the same md5 order, plus its keyboard and ARIA data. Each system with token sets contributes 10 tokens and their alias chains (`md5(token.id || 'deep-2')`). Each system with patterns contributes 3 patterns, and every system's facts (latest version, philosophy, principles) were checked.
2. **Live sources.** Every source was fetched over HTTPS at audit time: react-spectrum.adobe.com and react-aria.adobe.com `.md` pages, spectrum.adobe.com `.plain.html` fragments, `/deps/*/data/*.json` and `query-index.json`, and @adobe/spectrum-tokens, @adobe/spectrum-design-data, antd, antd-mobile, @mui/material, @mui/joy and nhsuk-frontend files at the pinned version on jsDelivr. Also fetched: GitHub raw files at the release tag (ant-design 6.7.0, ant-design-mobile v5.43.0, material-ui v9.5.0 and v5.17.1, base-ui v1.9.0, nhsuk-service-manual main), npm registry metadata, and each `docsUrl`. Fetches used curl with a disk cache and a gap of at least 1.1 s per host. No authentication or bypass was used.
3. **Comparison.** A script compared each sampled claim with the live source and recorded a verdict. Claims it could not settle automatically, and every `documented-none` or `verified` claim, were then resolved by hand against the source text. The criteria were: (a) the name exists; (b) `docsUrl` returns HTTP 200 and its title or h1 is the component; (c) variants, sizes and states appear in the source; (d) each property's name, type and default (and `required`, where stored) match the API table, JSON or macro options; (e) keyboard and ARIA entries appear in the accessibility source; (f) the description is a verbatim excerpt of at most 280 characters; (g) coverage states are honest; (h) a `verified` classification is backed by the source.
4. **Targeted adversarial checks** on the same sampled components covered the evidence URLs behind each claim, accessibility tables copied between components, allowed-value enumerations, and `not-documented` claims checked against the full page text, including JSX callouts. A refutation found this way counts in the same totals.
5. **Verdicts.** CONFIRMED: the claim matches the source. REFUTED: it does not; the row gives the claim, what the source actually says, and the source URL. UNVERIFIABLE: the claim could not be checked (none in this audit).
6. **Fixes.** Each refutation was traced to its root cause. Adapter bugs in scope were fixed and covered by a regression test in `tests/unit/adapters/audit-deep2.test.ts`, then dry-run (`scripts/adapter-dry-run.ts`) and re-ingested with `npm run ingest -- --system <slug> --inline`. After re-ingestion the same sample was re-dumped and re-verified with the same script and the same manual rules.

## Refuted claims, root causes and fixes

### F1. Spectrum token evidence cited the wrong file

- **Systems:** adobe-spectrum. **Sampled refutations:** 5 (Search field, Alert banner, Action bar, Status light, Help text). **Catalog-wide extent (before fix):** 83 adobe-spectrum components carried `tokens` evidence pointing at accordion.json.
- **Claimed vs actual:** the `tokens` evidence for every component cited `@adobe/spectrum-tokens@15.6.0/src/accordion.json`. That file holds only tokens with `"component": "accordion"`; Search field's single token is in `src/search-field.json`, Alert banner's 9 in `src/alert-banner.json`, and so on.
- **Source:** [https://cdn.jsdelivr.net/npm/@adobe/spectrum-tokens@15.6.0/src/accordion.json](https://cdn.jsdelivr.net/npm/@adobe/spectrum-tokens@15.6.0/src/accordion.json) vs [https://cdn.jsdelivr.net/npm/@adobe/spectrum-tokens@15.6.0/src/search-field.json](https://cdn.jsdelivr.net/npm/@adobe/spectrum-tokens@15.6.0/src/search-field.json)
- **Root cause:** `normalize-design.ts` built one `tokensEv` from the alphabetically first token file and reused it for every component.
- **Fix:** `tokens.ts` `buildTokenSets` now returns `componentTokenFiles` (each `component` field mapped to the evidence of the files that declare its tokens). `buildComponent` emits one `tokens` evidence row per actual file.
- **Regression test:** `audit-deep2.test.ts` › "does not publish Button's keyboard table as Meter's; token evidence names the file that holds the tokens"
- **Verified after re-ingest:** sampled 5/5 now cite their own file (e.g. `src/search-field.json`). Catalog-wide: all 86 `tokens-json` evidence rows of adobe-spectrum components were fetched, and each cites a file that declares tokens with that component's `component` field (0 mismatches)

### F2. Accessibility tables copied from another component published as the component's own

- **Systems:** adobe-spectrum, react-spectrum. **Sampled refutations:** 3 (Search field and Help text on adobe-spectrum, TableView on react-spectrum). **Catalog-wide extent (before fix):** adobe-spectrum: 13 components (12 copies of Button's fragment and 1 of Tooltip's); react-spectrum: 12 components (11 Button copies and TableView).
- **Claimed vs actual:** Search field, Help text, Meter, Progress bar, Field label and others published the keyboard map "Tab: Moves focus onto or off of the button. / Space or Enter: Executes the button action", plus Button's WCAG list, with `keyboard: documented`. TableView published Tooltip's "Tab: … shows the tooltip / Esc: Hides the tooltip".
- **Source:** spectrum.adobe.com serves `/fragments/components/{search-field,help-text,meter,progress-bar,field-label,…}/accessibility.plain.html` byte-identical to `/fragments/components/button/accessibility.plain.html` (same md5 `e3f28cb9…`). The table fragment repeats Tooltip's tables, with one cursor-table header changed. The copy is faithful to the source, but it is a site template and says nothing about these components.
- **Root cause:** Each accessibility fragment was trusted as component-specific.
- **Fix:** `site.ts` `templatedA11yFragments` groups accessibility fragments by their parsed keyboard and WCAG content. In a group of 2 or more, the owner is the single component whose name the copied text mentions (button, tooltip); every other member is treated as a copy. Copies publish no keyboard or WCAG rows from the fragment (design-data roles and WCAG still apply), and their keyboard and accessibility coverage is `not-extracted`. Groups without one clear owner are left unchanged. The adobe-spectrum normalize step logs the count.
- **Regression test:** `audit-deep2.test.ts` › "maps verbatim copies to the component the copied text is about", "leaves shared fragments alone …", "does not publish Button's keyboard table as Meter's …", "does not publish Button's keyboard table on Meter's React Spectrum page"
- **Verified after re-ingest:** the adobe-spectrum ingest logs "13 accessibility fragments are verbatim copies" and react-spectrum updated 16 records. Search field, Help text and TableView keyboard are now null with coverage `not-extracted`, and Button and Tooltip keep their own tables. Catalog-wide, no two adobe-spectrum or react-spectrum components publish the same keyboard table any more

### F3. MUI allowed values taken from inside object types

- **Systems:** mui, joy-ui (base-ui unaffected). **Sampled refutations:** 1 (Snackbar `anchorOrigin`). **Catalog-wide extent (before fix):** 10 props: mui 6 (Snackbar `anchorOrigin`, Popover `anchorOrigin`/`transformOrigin`, Popper `modifiers`/`popperOptions`, Slider `slotProps`) and joy-ui 4 (Snackbar `anchorOrigin`/`slotProps`, Menu and Tooltip `modifiers`). base-ui: 0.
- **Claimed vs actual:** Snackbar `anchorOrigin` was published with `allowedValues = ["left"]`. The type is the shape `{ horizontal: 'center' | 'left' | 'right', vertical: 'bottom' | 'top' }`, so the prop has no literal allowed values, and "left" is a fragment of a naive split on `|`. Popover `anchorOrigin` and `transformOrigin`, Popper `modifiers` and `popperOptions`, and Slider `slotProps` had the same defect.
- **Source:** [snackbar.json @ v9.5.0](https://raw.githubusercontent.com/mui/material-ui/v9.5.0/docs/pages/material-ui/api/snackbar.json)
- **Root cause:** `mui/shared.ts` `literalUnion` split the whole type string on every `|`.
- **Fix:** New `topLevelUnion` splits only at depth 0, outside `{} [] () <>`, quotes and `=>`. `literalUnion` keeps only literal alternatives of the type itself. The same function drives MUI variant and size extraction.
- **Regression test:** `audit-deep2.test.ts` › "mui: allowed values come from top-level literal alternatives only" (3 cases)
- **Verified after re-ingest:** Snackbar `anchorOrigin` allowedValues is null; real unions (Stack `direction`, `timeout` 'auto') are unchanged

### F4. Base UI required marker published as part of the prop name

- **Systems:** base-ui. **Sampled refutations:** 1 (Meter `Root.value*`). **Catalog-wide extent (before fix):** 13 props in 11 base-ui components (`Collection.children*`, `Root.value*`, `Tab.value*`, …).
- **Claimed vs actual:** prop `Root.value*` with `required` unknown. The generated API table row is `value\*`: the asterisk marks a required prop.
- **Source:** [meter/types.md @ v1.9.0](https://raw.githubusercontent.com/mui/base-ui/v1.9.0/docs/src/app/(docs)/react/components/meter/types.md)
- **Root cause:** `baseui.ts` `parseBaseTypes` kept the cell text verbatim, and `normalize-base.ts` hard-coded `required: null`.
- **Fix:** The trailing `*` is stripped from the name and sets `required: true`. Unmarked props stay `null` (unknown), because the table never says "optional".
- **Regression test:** `audit-deep2.test.ts` › "reads the trailing * as the required marker …"
- **Verified after re-ingest:** Meter now publishes `Root.value` with required=true; no prop name ends in `*`

### F5. Base UI accessibility guidance cut to its lead-in

- **Systems:** base-ui. **Sampled refutations:** 2 (Toolbar guidance, Toolbar keyboard coverage). **Catalog-wide extent (before fix):** 1 component (Toolbar).
- **Claimed vs actual:** Toolbar guidance was only "To ensure that toolbars are accessible and helpful, follow these guidelines:", and keyboard was `not-documented`. The guideline it introduces ("Use inputs sparingly: Left and right arrow keys are used … to navigate among controls in horizontal toolbars") was dropped.
- **Source:** [toolbar/page.mdx @ v1.9.0](https://raw.githubusercontent.com/mui/base-ui/v1.9.0/docs/src/app/(docs)/react/components/toolbar/page.mdx)
- **Root cause:** Only usage-guideline blocks matching an accessibility keyword were kept, so the list items after a matching lead-in were lost. "arrow keys" was not a keyword.
- **Fix:** `a11yUsageBlocks`: an accessibility lead-in ending in `:` carries the blocks that follow it in the section, and `arrow keys` and `cursor keys` count as accessibility text. Keyboard entries are then read from those blocks.
- **Regression test:** `audit-deep2.test.ts` › "keeps the guidelines an accessibility lead-in introduces"
- **Verified after re-ingest:** Toolbar guidance includes "Use inputs sparingly: …" and keyboard is `documented` (Arrow keys)

### F6. MUI keyboard interactions in accessibility prose marked not-documented

- **Systems:** mui, joy-ui. **Sampled refutations:** 1 (Snackbar keyboard coverage). **Catalog-wide extent (before fix):** mui: Snackbar `not-documented` → `documented` (Escape) and Alert `not-documented` → `not-extracted` (its Accessibility section discusses keyboard focus without naming keys); joy-ui: Alert `not-documented` → `not-extracted`.
- **Claimed vs actual:** Snackbar keyboard was `not-documented`, but its Accessibility section says "The user should be able to dismiss Snackbars by pressing Escape."
- **Source:** [snackbars.md @ v9.5.0](https://raw.githubusercontent.com/mui/material-ui/v9.5.0/docs/data/material/components/snackbars/snackbars.md)
- **Root cause:** `markdown.ts` `parseA11y` read keys only from a `### Keyboard` subsection.
- **Fix:** Without a Keyboard subsection, sentences in the Accessibility section that name a key and describe pressing it become keyboard entries. Prose that mentions the keyboard without naming keys yields `not-extracted` instead of `not-documented`.
- **Regression test:** `audit-deep2.test.ts` › "extracts 'dismiss Snackbars by pressing Escape' …", "does not read a capitalized word as a key …"
- **Verified after re-ingest:** Snackbar keyboard is `documented`: Escape, "The user should be able to dismiss Snackbars by pressing Escape."

### F7. Ant Design state coverage `not-documented` while state props exist

- **Systems:** ant-design, ant-design-mobile. **Sampled refutations:** 1 (Steps). **Catalog-wide extent (before fix):** ant-design: 13 components (Steps, Progress, Result, QR code, Menu, Tabs, Typography, TreeSelect, Mentions, Image, Timeline, Alert, ConfigProvider); ant-design-mobile: 11 components. All went from `not-documented` to `not-extracted`.
- **Claimed vs actual:** Steps states were `not-documented`. The API documents `status` ("can be set to one of the following values: `wait` `process` `finish` `error`", type `string`) and `items[].disabled`.
- **Source:** [steps/index.en-US.md @ 6.7.0](https://raw.githubusercontent.com/ant-design/ant-design/6.7.0/components/steps/index.en-US.md)
- **Root cause:** States were derived only from boolean props of the component or literal-typed `status` props, and every other case was labelled `not-documented`.
- **Fix:** `props.ts` `unextractedStateProps`: when no state is derived but a non-deprecated `status` prop or a state-named prop exists (including on sub-parts), coverage is `not-extracted`. No state values are invented.
- **Regression test:** `audit-deep2.test.ts` › "flags Steps `status` … and sub-part `disabled`"
- **Verified after re-ingest:** Steps states coverage is `not-extracted`

### F8. antd-mobile CSS variable attributed to "Ref"

- **Systems:** ant-design-mobile. **Sampled refutations:** 1 (token `ref.background`). **Catalog-wide extent (before fix):** 1 token (`ref.background`).
- **Claimed vs actual:** token `ref.background`. `--background` is SwipeAction's CSS variable; its `### CSS Variables` table just follows the `## Ref` methods table.
- **Source:** [swipe-action/index.en.md @ v5.43.0](https://raw.githubusercontent.com/ant-design/ant-design-mobile/v5.43.0/src/components/swipe-action/index.en.md)
- **Root cause:** The table owner was the nearest parent heading that looked like a component name, and `Ref` matched.
- **Fix:** `mobileCssVarOwner` excludes API-section headings (Ref, Props, Events, Methods, API, Types, Interfaces, Hooks). Real sub-components such as `## SpinLoading` still own their tables.
- **Regression test:** `audit-deep2.test.ts` › "attributes SwipeAction's variables …"
- **Verified after re-ingest:** token published as `swipe-action.background`; `ref.*` no longer exists

### F9. React Aria accessibility callouts ignored (`accessibility: not-documented`)

- **Systems:** react-aria (react-spectrum pages checked: none affected in the sample). **Sampled refutations:** 4 (FileTrigger, Tooltip, Button, Modal). **Catalog-wide extent (before fix):** 10 of 57 react-aria components (published accessibility coverage went from 6 to 16 documented).
- **Claimed vs actual:** accessibility was `not-documented`. Each page carries an `<InlineAlert><Heading>Accessibility</Heading>…` callout, for example FileTrigger: "Any `<Pressable>` child must have an interactive ARIA role or use an appropriate semantic HTML element so that screen readers can announce the trigger."
- **Source:** [FileTrigger.md](https://react-aria.adobe.com/FileTrigger.md), [Tooltip.md](https://react-aria.adobe.com/Tooltip.md), [Button.md](https://react-aria.adobe.com/Button.md), [Modal.md](https://react-aria.adobe.com/Modal.md)
- **Root cause:** The markdown line scanner drops JSX blocks, so callouts never reached the prose sections that accessibility guidance is read from.
- **Fix:** `docs-md.ts` `inlineAlerts` reads InlineAlert callouts outside fenced code and keeps code spans verbatim, so `<Pressable>` is not lost. `parseDocsMd` exposes them as `callouts`, and `normalize-react.ts` treats Accessibility callouts as accessibility prose. Spectrum adapter version bumped to 1.0.1 so parsed fragments are rebuilt.
- **Regression test:** `audit-deep2.test.ts` › "reads callouts outside code and keeps code spans verbatim"
- **Verified after re-ingest:** FileTrigger, Tooltip, Button and Modal now publish `accessibility: documented`, with guidance starting "Accessibility: …" taken from the callout

## Open issues

- **R1, open (shared govuk code, owned by deep-1):** NHS Footer accessibility guidance is the single word "accessibility", taken from the footer's list of link examples (`<li>accessibility</li>`), with guidance coverage `documented`. Root cause: `src/ingestion/adapters/govuk/docs.ts` `sentencesMatching()` accepts a bare list item as a sentence when it matches `A11Y_RE`. Proposed fix: skip candidates shorter than 4 words (`if (s.trim().split(/\s+/).length < 4) continue;`) or skip items of link lists. Then the footer gets guidance `not-documented`, because the page has no footer accessibility guidance. Still REFUTED in this audit.
- **R2, open (shared govuk code):** `src/ingestion/adapters/govuk/normalize.ts` line 384 writes the tokens-evidence location `(helper calls and $govuk-* settings)` for every profile. For nhs-design-system the file uses `nhsuk-*` helpers and `$nhsuk-*` settings. Proposed fix: interpolate the profile prefix. Still REFUTED.
- **R3, suggestion (engine, shared):** add a generic validation warning in `src/ingestion/engine/validate.ts` when 3 or more components of one system publish byte-identical keyboard tables. The Spectrum template copies (F2) went unnoticed because nothing checks for this across components, and other adapters could have the same pattern.
- **R4, engine (shared): `--inline` runs race the background worker.** `processRunInline` claims jobs from the shared `ingest` queue, so a long-running `npm run worker` can take the parse and publish jobs of an inline run. That worker keeps the adapter code it loaded at start-up. Here it published the pre-fix ant-design and ant-design-mobile output (runs `907fff33` and `7a80ac1f`, `updated=0`) while reporting success, and the inline caller could not tell. Proposed fix (`src/ingestion/engine/worker.ts` / `queue.ts`): put the jobs of `--inline` runs on a private queue, or record `locked_by` on the run and refuse foreign workers. Also have the worker stamp jobs with the adapter `version` it has loaded and release a job whose adapter version differs from the version recorded in the job payload at enqueue time. The two systems were then re-run in-process, and the after-fix results come from those runs.
- **Source-side notes (not ATLAS defects):** spectrum.adobe.com publishes Button's accessibility fragment verbatim for 12 other components and Tooltip's for Table. Adobe would need to fix the source; ATLAS now leaves these components' keyboard data `not-extracted` instead of repeating the copy. Joy UI's npm `latest` (5.0.0-beta.52) dates from 2025-03-18, and its docs state that development is on hold. ATLAS reports both as published.
- **Not re-ingested:** nhs-design-system (no adapter change in scope). The generic systems were not touched, because the background worker was re-ingesting them.
- **Limitations:** 6 components per system is a small sample, so the catalog-wide extent of each defect class was measured separately, by diffing each dry-run bundle against `atlas` (the extents quoted under F1–F9). Properties beyond the 3 checked per component, and tokens beyond the 10 per system, were not compared one by one.
